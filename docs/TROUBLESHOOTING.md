# Troubleshooting

프로젝트를 진행하며 발생한 주요 문제와 해결 과정은 별도 문서로 정리했습니다.

## 1. SSR 페이지를 SSG/ISR로 전환하며 사용자별 데이터 분리

### 문제

상품 페이지를 SSR로 렌더링하면서 매 요청마다 상품 데이터와 사용자별 위시 여부를 함께 조회하고 있었습니다. 이 구조에서는 로그인 쿠키/헤더에 의존하기 때문에 SSG/ISR 적용이 어려웠습니다.

### 원인

상품 기본 정보는 모든 사용자에게 동일하지만, 위시 여부는 로그인 사용자마다 달라지는 데이터였습니다. 두 데이터를 하나의 요청에서 함께 처리하면서 정적 생성 대상과 사용자별 동적 데이터가 결합되어 있었습니다.

### 해결

- 메인 페이지, 상품 카테고리 페이지, 상품 상세 페이지를 정적화 가능 대상으로 분류
- `revalidate`, `generateStaticParams`, `dynamicParams`를 활용해 SSG/ISR 적용
- 상품 공통 데이터와 사용자별 위시 여부 요청 분리
- 인증 토큰이 필요한 데이터는 클라이언트 요청 또는 별도 API로 분리

### 결과

상품 페이지의 캐싱 가능 범위를 넓히고, 사용자별 데이터 때문에 전체 페이지가 SSR에 묶이는 문제를 줄였습니다.

## 2. 빌드 환경에서 middleware 토큰 재발급 중복 요청 문제

### 문제

초기에는 middleware에서 페이지 접근 시 토큰 재발급과 인증 검사를 함께 처리했습니다. 개발 환경에서는 문제가 없었지만, 빌드 환경에서는 페이지 이동이나 병렬 요청 상황에서 refresh 요청이 중복으로 발생해 인증 오류가 발생하는 경우가 있었습니다.

### 원인

middleware는 페이지 요청 흐름에서 실행되며, 빌드 환경에서는 여러 요청이 동시에 발생할 수 있었습니다. 이때 middleware에서 토큰 재발급까지 처리하면 동일한 refresh token으로 여러 재발급 요청이 발생하고, 먼저 갱신된 토큰 이후의 요청이 실패할 수 있었습니다.

### 해결

- middleware에서는 토큰 재발급을 제거하고 인증 검사만 수행하도록 역할을 축소
- 실제 토큰 재발급은 Next.js API Route의 `withAuth`, `refreshAuthFromTokens`에서 처리
- API Route 내부에서는 `TokenRefreshLock`을 사용하여 동일 실행 컨텍스트 내 refresh 요청이 같은 Promise를 공유하도록 처리
- 사용자/판매자/관리자별 preset을 통해 인증 로직을 공통화

### 결과

middleware의 책임을 페이지 접근 제어로 단순화하고, 토큰 재발급은 API 요청 계층에서 안정적으로 처리하도록 분리했습니다.

## 3. API 요청 방식 중복과 오류 처리 표준화

### 문제

API마다 요청 데이터 형식과 헤더 설정이 달라 fetch 호출 코드가 반복되고, 오류 처리 방식도 일관되지 않았습니다.

### 원인

JSON, FormData, URLSearchParams, multipart 요청을 각각 컴포넌트나 서비스 함수에서 직접 처리하면서 요청 변환과 에러 처리 로직이 분산되었습니다.

### 해결

- `fetchFilter.ts`에서 요청 메서드별 공통 함수 구성
- `endpoints.ts`에서 API URL과 path parameter 관리
- 응답과 오류 형식을 표준화하여 React Query와 전역 error handler에서 공통 처리
- ISR/SSG 요청을 위해 `getCached`와 일반 요청 함수를 분리

### 결과

API 호출 코드의 중복을 줄이고, 요청 형식과 오류 처리 방식의 일관성을 확보했습니다.

## 4. 공통 다이얼로그와 도메인 모달 상태 분리

### 문제

처음에는 공통 다이얼로그와 도메인 모달을 하나의 Zustand store에서 관리했습니다. 하지만 특정 도메인 모달 내부에서 confirm 다이얼로그를 추가로 띄워야 하는 상황이 생기면서 모달 상태가 충돌하거나 흐름이 복잡해지는 문제가 있었습니다.

### 원인

성격이 다른 모달을 하나의 상태로 관리하면서, 도메인 모달과 공통 confirm/alert의 열림 상태와 전달 데이터가 서로 영향을 줄 수 있었습니다.

### 해결

- 공통 alert/confirm은 `DialogRoot`로 분리
- 특정 페이지/기능에서 사용하는 도메인 모달은 `DomainModalRoot`로 분리
- 각각의 Zustand store에서 open/close/result 상태를 독립적으로 관리
- 최상위 layout에서 두 Root 컴포넌트를 공통 렌더링

### 결과

도메인 모달 내부에서도 공통 confirm을 안정적으로 호출할 수 있게 되었고, 모달 상태 관리 흐름이 단순해졌습니다.

## 5. 장바구니 쿠폰 적용 상태 초기화 문제

### 문제

장바구니에서 쿠폰을 적용할 때 상품 선택, 옵션 변경, 상품 삭제, 쿠폰 다운로드 등 여러 동작이 발생하면 적용된 쿠폰 상태가 의도치 않게 초기화되거나, 반대로 초기화가 필요한 상황에서 이전 쿠폰 상태가 유지될 수 있었습니다.

또한 최대 할인 쿠폰 자동 적용 상태와 사용자가 직접 선택한 쿠폰 상태를 구분해야 했습니다.

### 원인

장바구니 쿠폰 상태는 단순히 쿠폰 하나의 선택 여부만으로 결정되지 않았습니다.

- 상품 선택 여부
- 상품 수량 및 옵션
- 판매자 쿠폰 / 장바구니 쿠폰 구분
- 중복 가능 / 중복 불가능 쿠폰 구분
- 다른 상품에서 이미 사용 중인 쿠폰 여부
- 최대 할인 자동 적용 여부
- 쿠폰 다운로드 후 장바구니 데이터 재조회 여부

위 조건들이 함께 영향을 주기 때문에, 장바구니 데이터를 다시 불러올 때마다 쿠폰을 항상 초기화하면 사용자 선택이 사라지고, 반대로 항상 유지하면 적용 불가능한 쿠폰이 남을 수 있었습니다.

### 해결

- `appliedProductCouponMap`으로 cartId별 적용 쿠폰을 관리
- 중복 불가능 쿠폰은 `unStackable`, 중복 가능 쿠폰은 `stackable`로 분리
- 최초 자동 적용된 최대 할인 쿠폰 조합은 `maxDiscountAppliedProductCouponMapRef`에 저장
- 현재 적용 쿠폰 조합과 최대 할인 조합을 비교하여 최대 할인 적용 여부 판단
- 사용자가 직접 쿠폰을 변경한 경우 `userCouponChanged`로 추적
- 상품 선택/옵션 변경 등 쿠폰 초기화가 필요한 동작에서는 안내 후 자동 적용 로직 재수행
- 위시 변경, 미선택 상품 옵션 변경, 쿠폰 다운로드처럼 쿠폰 초기화가 불필요한 동작은 `noResetCoupon`으로 예외 처리
- 이미 다른 상품에서 사용 중인 쿠폰은 `otherUsed`로 비활성화

### 결과

장바구니의 상품 상태가 변경되더라도 쿠폰 적용 상태를 예측 가능하게 관리할 수 있게 되었고, 최대 할인 자동 적용과 사용자 수동 선택을 구분하여 처리할 수 있었습니다.

## 6. 구매 진행 중 재고 선점 문제

### 문제

사용자가 구매 페이지에 진입한 후 결제 전까지 재고를 확보하지 않으면, 여러 사용자가 동시에 같은 재고를 구매할 수 있는 문제가 있었습니다.

### 원인

단순히 결제 완료 시점에만 재고를 차감하면, 결제 직전 단계에서 다른 사용자가 같은 수량을 선택하는 상황을 막기 어렵습니다.

### 해결

- 구매 페이지 진입 시 `stock_hold` 생성 API 요청
- holdId를 기준으로 구매 페이지의 상품/쿠폰/재고 상태 관리
- hold 상태와 만료 시간을 기준으로 백엔드에서 유효 선점 수량 계산
- 실시간 재고 조회 시 hold 수량 반영
- 결제 완료 또는 오류/만료 시 hold 상태 정리
- 장바구니 구매 시 `cartId`, 오류 복귀를 위한 `returnUrl` 관리

### 결과

구매 진행 중인 수량을 재고 계산에 반영하여 재고 초과 주문 가능성을 줄였습니다.
